1. Нарушение безопасности при подмене GET/POST
Суть нарушения: Использование GET-запросов для изменения данных (например, GET /api/v1/delete_user?id=10).

Что ломается на практике:

Кеширование: Браузеры, CDN (Cloudflare) и прокси-серверы обожают кешировать GET-запросы. В итоге первый запрос удалит пользователя, а второй — просто вернет старый ответ из кеша, даже не дойдя до бэкенда.

Веб-краулеры (Поисковые роботы): Гугл-бот или Яндекс-робот, индексируя ваш сайт, пойдет по всем ссылкам GET. Если удаление или покупка висит на GET, робот просто «выкосит» или скупит всю вашу базу данных за один проход.

2. Потеря идемпотентности (Смерть для биллинга и распределенных систем)
Суть нарушения: Делать POST там, где нужен PUT или PATCH, либо путать их семантику.

Что ломается на практике:

Если сеть моргнула во время отправки POST /orders (создание заказа), фронтенд или мобилка не знают, дошел ли запрос. Они повторяют его (retry).

Если бэкенд не спроектирован по REST-принципам идемпотентности, система создаст два или три одинаковых заказа и спишет деньги несколько раз. REST четко разделяет: POST — не идемпотентен (создает новый ресурс), PUT/PATCH — должны быть идемпотентными (повтор безопасен).

3. Игнорирование статус-кодов (Ужас фронтендера)
Суть нарушения: Возвращать всегда 200 OK, а саму ошибку прятать внутри JSON ({ "success": false, "error": "Unauthorized" }).

Что ломается на практике:

Прокси и API Gateways (Nginx, Kong): Они ориентируются только на HTTP-статусы. Если бэкенд упал по таймауту или там упала БД, но код отдал 200 OK, балансировщик решит, что сервер «живой и здоровый», и продолжит лить на него трафик вместо того, чтобы переключить на резерв.

Код фронтенда превращается в спагетти: Вместо стандартного перехвата ошибок в catch блоке по HTTP-статусу (401, 403, 500), фронтендеру приходится парсить тело каждого успешного ответа и писать бесконечные if (data.status === 'error').

4. Нарушение Stateless (Крах масштабирования)
Суть нарушения: Хранить состояние клиента (сессии, промежуточные шаги создания заказа) в оперативной памяти конкретного сервера.

Что ломается на практике:

Вы не сможете просто так поднять еще 5 копий вашего сервиса в Kubernetes. Если запрос пользователя уйдет на соседний под — система его «забудет» и выплюнет 401 Unauthorized.

Приходится внедрять сложные костыли вроде Sticky Sessions на балансировщике, что убивает саму идею легкого горизонтального масштабирования.


Как разработчики «сломали» Stateless в HTTP
Когда веб начал развиваться, бизнесу потребовалось сохранять состояние (например, корзину покупок или авторизацию). Поскольку HTTP этого не умел, инженеры придумали костыль: Куки (Cookies) и Сессии (Sessions).
